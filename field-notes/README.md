# Field notes

The principles are the cookbook. These are the scribbles in the margin: how specific tools behaved when I used them, written down with the date I checked.

Field notes are not rules. The [playbook](../PLAYBOOK.md) says what must be true, whatever the tool. A field note says how one tool gets you there, today. Tools change fast, so these notes go out of date.

## How to read a note

- **Each note covers one tool** and says when it was checked, and against what (the tool's docs, a version, a real project).
- **When a note and the tool's own docs disagree, trust the docs.** Then fix the note, or mark it as outdated.
- **Notes link to the vendor's docs** instead of copying them, so there is less to go stale.
- **A note is an observation, not evidence for a rule.** When the same practice holds across tools and projects, it can become a playbook rule.

## How notes relate to the rest

1. A project logs friction and surprises as they happen, in its own `dev/tool-feedback.md` (playbook rule 7).
2. What's worth sharing is cleaned up and kept here, one file per tool.
3. What holds across tools and projects graduates to the playbook.
